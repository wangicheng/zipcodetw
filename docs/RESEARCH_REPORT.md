## 1. 研究背景與既有解決方案分析

台灣 3+3 碼郵遞區號系統涵蓋全台 79,876 筆門牌對照規則。其結構包含單雙號、連號、附號（如 `1之23號`）、樓層與地下室（如 `2樓以上`、`地下1樓至1樓`）等多維度條件。

在台灣地址解析與 3+3 郵遞區號對照的應用場景中，常見的解決方案與其架構特點如下：

### 1.1 關聯式資料庫查詢 (RDBMS / SQLite)

- **原理**：將中華郵政官方 `rall1.dbf` 資料匯入關聯式資料庫，透過 SQL `LIKE` 或正則表達式進行門牌匹配。
- **主要特點與局限**：
  1. **依賴資料庫服務**：需依賴外部資料庫伺服器或本地 SQL 引擎進程，無法以極度輕量形式直接嵌入無伺服器邊緣運算或瀏覽器離線執行。
  2. **檢索機制**：若未建置專屬倒排索引，純 SQL 文字搜尋在多維度門牌比對時較難以輕量位元運算直接完成。

### 1.2 官方線上網頁表單查詢與爬蟲串接 (JSP POST / Web Scraping)

- **原理**：中華郵政官方並未直接提供開放的 REST API 或 JSON API 端點，而是於官方網站提供「郵遞區號查詢」JSP 網頁介面。開發者若要線上呼叫，通常是透過 HTTP POST 表單向 `https://www.post.gov.tw/post/internet/Postal/index.jsp?ID=208` 發送查詢請求：
  ```javascript
  fetch('https://www.post.gov.tw/post/internet/Postal/index.jsp?ID=208', {
    headers: {
      'content-type': 'application/x-www-form-urlencoded',
    },
    referrer: 'https://www.post.gov.tw/post/internet/Postal/index.jsp?ID=208',
    body: 'list=5&list_type=2&firstView=4&firstView2=1&city2_zip6=%E8%87%BA%E5%8C%97%E5%B8%82&cityarea2_zip6=%25&road_zip6=&sec_zip6=%25&Submit=%E6%9F%A5%E8%A9%A2',
    method: 'POST',
  });
  ```
- **主要特點與局限**：
  1. **非結構化資料與 HTML 剖析開銷**：此介面回傳為包含完整網頁樣式與結構之 HTML（單次查詢約 267~294 KB），呼叫端必須額外實作 HTML 表格爬蟲剖析器以提取郵遞區號。
  2. **強依賴外網與限速風險**：無法在無外網環境或離線前端執行，且易受官方伺服器負載、連線逾時及請求限速影響。
  3. **無法用於百萬級大量批次清洗**：若需對百萬級門牌進行批次地址標準化與郵遞區號補全，連續發送大量 HTTP POST 請求將造成巨大延遲與被伺服器阻擋風險。
- **實際基準測試數據**（經由 [official_web.ts](../packages/zipcodetw/benchmarks/official_web.ts) 對全台 22 處代表性門牌進行真實 HTTP 實測）：
  - **單次回傳 HTML 體積**：平均 **275.00 KB**（中位數 275.51 KB，最小 267.29 KB，最大 294.06 KB）。
  - **HTTP 網路往返延遲 (RTT)**：平均 **253.61 ms**（中位數 245.55 ms，P95 311.27 ms）。
  - **客戶端 HTML 剖析耗時**：平均 **0.163 ms (163.5 µs)**。
  - **端到端單次查詢總延遲**：平均 **253.77 ms**。

### 1.3 傳統記憶體 JSON 物件樹展開法

- **原理**：將門牌對照表於建置期轉為 JSON 格式（如 6~12 MB 之 JSON 檔案），並在應用程式啟動時透過 `JSON.parse()` 將完整資料展開為記憶體中的 JavaScript 物件與 Map 搜尋樹。
- **主要特點與局限**：
  1. **傳輸體積龐大**：前端瀏覽器需下載數 MB 的 JSON 或 JS 檔，消耗使用者頻寬。
  2. **記憶體與垃圾回收負擔**：將數萬筆規則展開為物件與字串時，會產生逾 44,000 個字串物件與 79,000 個規則物件，導致 V8 Heap 堆記憶體淨增長約 35.7 MB、進程總記憶體高達 164.8 MB。
  3. **冷啟動延遲較高**：JSON 解析與記憶體物件樹建置耗時約 246 ms，在無伺服器邊緣運算環境中冷啟動開銷明顯。

## 2. 二進位資產架構與核心技術

為了在保持 100% 離線可用與微秒級檢索的前提下大幅降低記憶體開銷與冷啟動延遲，ZipCodeTw 設計了**全二進制零展開架構**。

系統將 79,876 筆官方資料編譯為兩份自訂二進位資產：`address_prefixes.bin` 與 `zipcode_rules.bin`。

```text
[ 中華郵政 rall1.dbf (34.99 MB / 去英文欄位 26.20 MB) ]
         │
         ▼ (純 TypeScript DBFReader 記憶體解析)
[ 記憶體 RawAddress 陣列 ]
         │
         ▼ (二進制編譯器)
┌─────────────────────────────────────┬─────────────────────────────────────┐
│    address_prefixes.bin (1.24 MB)   │      zipcode_rules.bin (1.33 MB)    │
│  (區塊化前綴編碼 + 預建倒排索引)    │    (定長索引表 + 位元遮罩標頭)      │
└─────────────────────────────────────┴─────────────────────────────────────┘
         │                                     │
         └──────────────────┬──────────────────┘
                            ▼
           [ BinaryPrefixSearchEngine ]
           [     BinaryRuleStore      ]
           (靜態 Uint8Array 零複製比對)
```

### 2.1 門牌前綴區塊化增量前綴編碼 (Front Coding)

台灣地名與門牌具有極高的行政區劃與路名前綴重疊性（例如 `臺北市大安區和平東路一段`、`臺北市大安區和平東路二段`、`臺北市大安區和平東路三段` 等，前面 9 個字元完全一致）。若採用傳統平鋪字串陣列儲存全台 44,658 條不重複門牌前綴，會產生大量重複的 UTF-8 位元組。

本專案採用增量前綴編碼（Front Coding）配合區塊化設計進行資料壓縮與隨機存取：

#### 2.1.1 Front Coding 演算法與位元組標頭結構

Front Coding 的核心原則為：先將全量門牌前綴字串依字典序排序，後續字串僅需記錄「與前一條字串相同的公共前綴位元組長度 (`shared`)」以及「剩餘差異尾綴 (`remainder`)」。

實務上，台灣門牌前綴極少超過 20 個字（約 60 個 UTF-8 位元組），遠小於 `uint8` 標頭的 255 位元組上限。因此，系統直接使用 UTF-8 位元組長度作為 `shared` 單位：

| 欄位名稱 |          型態 / 長度          | 單位與說明                              |
| :------- | :---------------------------: | :-------------------------------------- |
| `shared` |       `uint8` (1 byte)        | 與同區塊前一條字串重疊的 UTF-8 位元組數 |
| `remLen` |       `uint8` (1 byte)        | 剩餘差異字串在緩衝區中佔用的位元組長度  |
| `remStr` | `Uint8Array` (`remLen` bytes) | 剩餘差異字串之 UTF-8 原始位元組串流     |

> **區塊錨點字串 (offsetInBlock = 0)**：每個區塊的首條字串寫入 2 位元組 `uint16` 全量 UTF-8 位元組總長度 `anchorLen`，後隨全量 UTF-8 位元組串流。

**純 Uint8Array 延遲解碼效能**：

在解碼端 [BinaryPrefixSearchEngine](../packages/zipcodetw/src/core/BinaryPrefixSearchEngine.ts) 中，區塊解碼完全在 `Uint8Array` 靜態記憶體緩衝區上進行位元組複製，無須為中間字串產生 JavaScript 字串物件，僅在抵達目標 ID 時呼叫一次 `TextDecoder` 解碼：

```typescript
currentBytes.set(this.buffer.subarray(cursor, cursor + remLen), sharedBytes);
currentLen = sharedBytes + remLen;
```

#### 2.1.2 區塊化設計與 $O(1)$ 隨機存取解碼

傳統 Front Coding 的局限在於：若要解碼第 $N$ 條字串，必須從第 1 條字串開始依序遞迴解碼至第 $N$ 條，無法進行任意目標的隨機存取。

為了兼顧高壓縮率與隨機讀取效能，系統實作了區塊化設計（以 $K$ 條字串劃分為一個獨立區塊）：

- **區塊獨立性**：每個區塊的第一條字串（`offsetInBlock = 0`）固定為錨點字串，`shared` 長度強制重置為 `0` 且不依賴前一區塊，使各個區塊具備完全獨立解碼的能力。
- **定長區塊索引表**：在二進位標頭後維護連續的 8 位元組定長索引項（`relTextOffset: uint32`, `blockLen: uint16`, `reserved: uint16`）。
- **隨機定點解碼流程**：當查詢引擎需要取得特定 ID (`targetId`) 的字串時，可透過純位元運算瞬間定位：
  $$\text{blockIdx} = \lfloor \text{targetId} / K \rfloor, \quad \text{offsetInBlock} = \text{targetId} \pmod{K}$$
  引擎只需讀取該 `blockIdx` 的 `relTextOffset`，即可直接對該區塊內的字串進行單一區塊解碼，免除無關區塊的 I/O 與解碼負擔。

#### 2.1.3 區塊大小超參數敏感度分析

在區塊化架構中，區塊大小 $K$ 是影響資產體積與隨機解碼延遲的核心控制參數：

- **$K$ 越小**：區塊數越多，錨點字串與區塊索引表項目增加，檔案體積變大，但單次解碼需巡檢的字串較少。
- **$K$ 越大**：前綴重疊鏈拉長，體積縮小，但單次隨機解碼時需巡檢更多字串，導致解碼運算耗時上升。

## 2.2 預建二進位倒排索引與檢索引擎

ZipCodeTw 於編譯時期為全台門牌前綴中出現過的 **1,807 個 Unicode 字元** 事先建置了二進位倒排索引（Inverted Index），配合 TypedArray 指標運算達成微秒級比對。

#### 2.2.1 倒排索引資料結構

`address_prefixes.bin` 包含以下二進位結構：

1. **字元對照表**：
   包含 1,807 個字元的定長 10 位元組結構陣列（已依 Unicode `charCode` 排序）：
   - `charCode` (`uint16`)：Unicode 字元編碼
   - `postingOffset` (`uint32`)：該字元倒排清單在緩衝區中的位元組偏移量
   - `postingLen` (`uint32`)：包含該字元的前綴字串總數量
   - 支援二分搜尋 ($O(\log C)$)，可快速取得字元對應的倒排清單。

2. **倒排清單串流**：
   連續儲存每位字元出現過的所有前綴字串 ID（`Uint16Array` 串流）。

#### 2.2.2 雙指標交集與零展開搜尋演算法

當使用者輸入查詢地址（例如："臺北市大安區和平東路"）時，[BinaryPrefixSearchEngine](../packages/zipcodetw/src/core/BinaryPrefixSearchEngine.ts) 的檢索流程如下：

```text
[ 查詢字串 "大安和平" ]
        │
        ▼ (取得各字元 Uint16Array 倒排清單)
  L_大: [102, 105, 308, ...] (Len: 1,200)
  L_安: [102, 308, 412, ...] (Len: 850)
  L_和: [102, 510, ...]      (Len: 320)
  L_平: [102, 510, ...]      (Len: 180)
        │
        ▼ (依清單長度由短至長排序過濾)
  Sorted Lists: [L_平, L_和, L_安, L_大]
        │
        ▼ (TypedArray 雙指標線性交集)
  Candidate String IDs = [102]  (縮減至 1~3 條候選 ID)
        │
        ▼ (惰性解碼目標區塊)
  僅針對 ID 102 實施區塊 UTF-8 解碼，其餘 99.99% 字串保持 Uint8Array 狀態
```

1. **倒排清單檢索**：讀取查詢字元對應之二進位 `Uint16Array` 指標清單 $L_1, L_2, \dots, L_k$。
2. **長度排序優先過濾**：將清單按元素數量由短至長排序，率先以最少元素的清單縮小交集範圍。
3. **雙指標零配置交集**：
   實作 [intersectSortedUint16](../packages/zipcodetw/src/core/BinaryPrefixSearchEngine.ts) 方法，利用 TypedArray 指標在靜態記憶體緩衝區上進行雙指標線性交集：
   $$\text{Candidates} = L_1 \cap L_2 \cap \dots \cap L_k$$
   過程不建立任何 JavaScript `Set` 或 `Map` 物件，可在微秒級時間內將 44,658 條前綴字串過濾至僅 1 ~ 3 條候選 ID。
4. **惰性解碼驗證**：
   最終僅對過濾出的 1~3 條候選 ID 進行單一區塊 UTF-8 解碼與比對。其餘 99.99% 的前綴字串全程保持原生 `Uint8Array` 二進位狀態，達成 V8 堆記憶體 0 MB 展開。

### 2.3 門牌規則二進制與零複製比對 (`zipcode_rules.bin`)

全台 79,876 筆門牌規則編譯為 1.33 MB 二進位檔（`zipcode_rules.bin`）：

- **32 位元組標頭 (`ZPR1`)**：定義郵遞區號字典、大宗戶名稱池與規則索引表偏移。
- **10 位元組定長索引表**：每筆規則固定佔用 10 位元組（`part1Index: uint16`, `zipcodeId: uint16`, `bulkNameId: uint16`, `ruleStreamOffset: uint32`），可經由 $O(1)$ 指標移位讀取。
- **2 位元組控制標頭**：
  - `標頭位元組 1`：使用位元遮罩標示數值、最小值、最大值、奇偶性 (`parity`: 0=無, 1=單, 2=雙, 3=連) 與子號模式 (`subMode`: 0=無, 1=all, 2=sub_all)。
  - `標頭位元組 2`：以 4-bit Enum 編碼門牌單位 (`unit`: 1=號, 2=巷, 3=樓, 4=弄, 5=附號) 與結束單位。
- **零複製位元比對**：`BinaryRuleStore` 接收查詢門牌數值，直接於緩衝區偏移位進行位元遮罩運算，比對過程零物件配置。

### 2.4 純 TypeScript 資料處理與編譯腳本

用於套件發布前的資料擷取與資產編譯：

- 實作 [fetch_official_dbf.ts](../packages/zipcodetw/scripts/crawler/fetch_official_dbf.ts)，下載中華郵政官方 RAR 檔並解壓縮 (`node-unrar-js`)。
- 使用 Node/Bun 原生 `TextDecoder('big5')` 與 `DBFReaderTS` 解析 `rall1.dbf`。
- 解析門牌規則並編譯輸出二進位資產（`address_prefixes.bin` 與 `zipcode_rules.bin`），於套件發布時打包最新資料。

## 3. 解決方案綜合對比矩陣與實驗效能報告

### 3.2 儲存體積、網路傳輸壓縮率與控制變因消融實驗

#### 3.2.1 基準控制與去英文欄位消融實驗

在評估資料壓縮率時，為確保評測基準的公平性並消除潛在變因，本研究對中華郵政官方 `rall1.dbf` 原始檔進行了欄位結構剖析與消融實驗：

1. **官方原始 DBF 結構**：包含 37 個欄位，每筆紀錄長度為 438 位元組，全台 79,876 筆紀錄的檔案總體積為 **34.99 MB** (34,987,169 位元組)。
2. **英文欄位佔比**：原始資料包含 `EROAD` (70 位元組)、`ECITY` (15 位元組) 與 `EAREA` (25 位元組) 共 3 個英文欄位，單筆合計佔用 110 位元組，佔原始紀錄長度的 **25.11%**。
3. **去英文正規化 DBF**：完全剔除上述英文欄位後，每筆紀錄縮減為 328 位元組，DBF 總體積降至 **26.20 MB** (26,200,450 位元組)。
4. **最小化核心查詢 DBF**：若進一步極端精簡，僅保留郵遞區號解析必備之 6 個欄位（`CITY`, `AREA`, `ROAD`, `SCOOP`, `DEPARTMENT`, `ZIPCODE`），單筆紀錄為 153 位元組，DBF 體積為 **12.22 MB** (12,221,254 位元組)。

實驗證明，ZipCodeTw 雙二進位資產（合計 **2.57 MB**）即使在排除英文欄位的相同基準下，相較去英文官方 DBF 仍實現 **-89.73%** 的體積縮減；相較最小化 DBF 亦縮減 **-77.97%**。體積的大幅降低主要來自於前綴共享編碼與定長位元遮罩封裝，而非單純捨棄英文資訊。

#### 3.2.3 二進位資產相對於壓縮 JSON 的架構特質

在網路傳輸層面，雖然 JSON 格式經過 Brotli 壓縮後可達 560 KB 左右，但在執行階段架構上，二進位格式具備不同的特質：

1. **零物件配置與零反序列化開銷**：
   JSON 檔案下載至客戶端後，必須透過 `JSON.parse()` 將文字串流完全反序列化，在記憶體中建立約 8 萬筆 JavaScript 物件與字串節點，產生數十 MB 的堆記憶體佔用與垃圾回收負擔。ZipCodeTw 的二進位檔案直接載入為靜態記憶體緩衝區（ArrayBuffer / TypedArray），反序列化開銷為 0 毫秒。
2. **原生記憶體二分搜尋**：
   查詢引擎直接在 TypedArray 結構上執行二分搜尋與位元運算，無需在應用程式啟動時建置任何輔助物件樹，使冷啟動耗時自傳統 JSON 的 246 毫秒降至 12 毫秒。

#### 3.4.3 時間與空間之工程權衡分析

- **典型中位數查詢延遲僅 28.0 µs**：P95 延遲穩定控制在 71.6 µs 內，即使在多重巷弄附號等較複雜場景，平均延遲亦低於 0.1 ms。
- **堆記憶體 0 MB 展開**：相較於傳統 JSON 展開法需建立數萬個物件（35.74 MB 堆記憶體），二進位引擎在原生 TypedArray 緩衝區運作，完全消除垃圾回收停頓風險。

## 4. 結論

本專案系統性地分析了不同架構在台灣 3+3 郵遞區號解析上的特性與取捨：

1. **架構場景清晰劃分**：
   - 若為極低頻即時查詢且不希望維護本地資料庫，官方線上網頁查詢提供零客戶端儲存的便利性。
   - 若為離線檢索、邊緣運算節點或百萬級大量資料批次清洗，ZipCodeTw 的全二進制零展開架構提供 100% 離線可用、微秒級低延遲（中位數 28.0 µs）與極小記憶體開銷。
2. **緊湊封裝與零展開**：
   - 透過區塊化前綴編碼、預建倒排索引與定長規則索引表，將全台門牌資料壓縮至 783.27 KB (Brotli)，並在執行期保持靜態緩衝區直讀。
3. **客觀嚴謹的工程權衡**：
   - 二進位檢索引擎在具備 27,900 QPS 高吞吐與 28.0 µs P50 延遲的同時，換取了 12 ms 極速冷啟動、0 MB 堆記憶體展開與低於 9.3 MB 的進程記憶體佔用。
