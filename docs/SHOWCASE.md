# ZipCodeTw 專案技術亮點與研究成果

> **專案簡述**：ZipCodeTw 是一個針對台灣 3+3 郵遞區號（含 79,876 筆門牌規則與 44,658 條前綴）打造的高效能、全離線、微秒級解析引擎。透過自訂全二進制零展開架構，達成極致記憶體壓縮與極速冷啟動。

## 一、 中華郵政技術交流

- 曾與中華郵政資訊處郵務資訊科進行技術交流，官方回覆表示已將本專案二進位架構轉交協力開發廠商作為未來系統評估參考。

## 二、 應用情境與既有方案特點

台灣門牌規則結構包含單雙號、樓層、附號、跨單位起訖等非結構化描述。現有解析方案具備不同架構特質：

1. **官方線上網頁查詢 (JSP POST / 爬蟲串接)**：官方未提供專屬 REST/JSON API，而是提供官方網站 JSP 查詢介面（透過 HTTP POST 表單提交）。此方式適合極低頻即時查詢，用戶端免下載全量資料庫；但每次查詢需下載約 275 KB 的 HTML 網頁並進行剖析，平均端到端延遲約 253.77 ms，且無法應用於無外網環境或百萬級資料批次清洗。
2. **官方原始 DBF 資料集 (`rall1.dbf`)**：官方公開隨附之原始資料集為 34.99 MB（去英文欄位後為 26.20 MB），檔案體積較大且未經前綴壓縮，無法直接在現代 Web 前端或邊緣環境中以輕量方式載入。
3. **傳統記憶體 JSON 物件樹**：若將資料轉為 JSON 並於執行期透過 `JSON.parse()` 展開，會產生逾 12 萬個 JavaScript 物件，導致冷啟動耗時 246 ms，且 V8 Heap 堆記憶體淨增長 35.7 MB（進程總記憶體達 164.8 MB），在 Cloudflare Workers 等邊緣運算環境記憶體負擔較大。

## 三、 核心技術創新：全二進制零展開

ZipCodeTw 將全量門牌與條件編譯為兩份精簡二進位資產（`address_prefixes.bin` 與 `zipcode_rules.bin`），在執行期完全不解碼未查詢之資料，直接在原生記憶體緩衝區上進行指標運算：

### 1. 區塊化增量前綴編碼 ($K=64$)

- **前綴壓縮與隨機存取**：利用台灣地址字串高重疊特性進行前綴壓縮。每 64 條字串劃分為獨立區塊，首條為全量錨點，其餘僅記錄相對重疊長度。
- **惰性解碼**：查詢時以 $O(1)$ 定位區塊，僅單點解碼目標區塊（耗時約 $7.48 \ \mu\text{s}$），其餘 99.99% 字串全程保持二進位狀態。

### 2. 10-Byte 定長索引與 16-bit 位元遮罩比對引擎

- **瞬間定位**：每筆規則紀錄固定佔用 10 位元組，透過二分搜尋鎖定規則串流。
- **位元遮罩零複製驗證**：規則標頭採用 2 位元組位元遮罩標記條件（單雙號、範圍極值、樓層）。比對時直接執行位元運算，全程零物件宣告、零字串切割。

### 3. Chevrotain AST 門牌條件編譯器

- 於編譯期將官方 DBF 中非結構化中文描述（如 `"連 1之23號至 45號附號全"`）透過語法解析器轉為 AST，並直接壓裝為高密度二進位串流。

## 五、 系統工程與部署特點

1. **跨語言獨立規格**：自訂二進位格式獨立於特定程式語言，結構設計易於日後移植至 C/Rust 等原生語言配合記憶體映射（mmap）或 WebAssembly 使用。
2. **自動化編譯管線**：內建資料編譯管線。官方更新 DBF 資料時，只需執行腳本重新編譯二進位資產並發布，無須執行複雜的資料庫結構遷移（Schema Migration）。
